# 第一轮本地无付费服务压测报告

日期：2026-09-30（北京时间）。测试对象：本地 `main`，提交 `a34239ed0c33cc8c191f3649749783e476a0941e`。

**结论：本轮已执行完毕，部分通过。** 并发/用户队列/预览限额、幂等、撤销及任务恢复达到本轮检查要求；视频提交的过载响应明显过慢，且本地原始打码环境和头发处理存在兼容问题。不能将其表述为已经通过完整上线容量验收。

## 测试边界

- 本地 Windows 实例，单 Uvicorn 进程；没有连接或压测生产服务器。
- 实测环境：Windows build 26200、Python 3.10.21、20 个逻辑 CPU、15.72 GiB 物理内存。README 建议 Python 3.11+，本轮使用项目现有 `.venv`，未升级依赖。
- 实际运行项目 HTTP、鉴权/CSRF、SQLite、生产调度器、预览执行器和本地视频处理。
- 12 个新建普通测试账号；`APP_VIDEO_WORKERS=10`，每账号 `max_concurrent=1`、`max_queued=3`。排队额度特意缩小以验证边界，不代表线上用户当前配置。
- 独立目录：`storage/phase1-loadtest-20260930/`；不使用原 storage 的账号、模型配置和业务数据。
- 禁用 dotenv 加载，服务子进程只继承必要系统变量，使用空模型密钥和 mock 配置；Python socket 审计钩子拒绝非回环连接。FFmpeg 只处理本地文件。
- `VideoProvider.generate` 在测试进程中替换为可阻塞、延迟 0.4 秒并返回本地文件的模拟供应商。供应商调用次数、结果和恢复路径均记录事件；这些结果不能解释为真实模型吞吐量。
- 采用 `legacy_raw` 本地参考图路径，没有测试真实人物授权/自动入库、TOS、TikHub 或续写供应商。续写恢复逻辑另外运行现有模拟传输回归测试。
- 发压机与被测服务共用本机，负载规模较小，不能据此推算服务器或不同硬件的容量。

## 已发现的问题

### 1. 视频提交在突发负载下不能及时拒绝

同时发起 120 个逻辑提交（HTTP 客户端最多 100 个连接），分布于 12 个账号：

| 观察方式 | 接收 200 | 拒绝 409 | 客户端未取得 HTTP 响应 | P95 | 全部观察完成耗时 |
|---|---:|---:|---:|---:|---:|
| 首次，客户端超时参数 30 秒 | 46 | 54 | 20 | 35.989 秒 | 36.145 秒 |
| 保留首次结果后，另发 120 个新提交，超时参数延长至 60 秒 | 46 | 74 | 0 | 37.093 秒 | 37.245 秒 |

首次原始脚本把客户端异常记为 `code=0`，没有持久化异常类，因此不能将这 20 个结果解释为 HTTP 500 或全部认定为某一种超时。延长超时仅用于核对最终接收和拒绝，**不是修复，也不是通过过载响应验收**。

代码中队列检查位于 `ProductionStore.create_run`，路由在此之前已进行草稿、配置、素材等多项处理。它是下一步应分析的路径，但本轮没有性能剖析证据将全部延迟归因于某个函数或锁。

### 2. 视频等待队列缺少独立的全站总量上限

`app/production_router.py` 读取当前用户 `max_queued`；`app/production_store.py` 在该用户数据库内原子统计排队任务；`app/production_worker.py` 控制全局执行槽位。未发现独立的全站视频等待总量或等待时限准入检查。

本轮用户额度之和是 36，因此出现 10 个运行、36 个等待是现有规则的预期结果。账号增加后，允许的等待总量也会增长。不能把“每用户有限额”描述成“全站固定有界队列”。关闭鉴权的兼容模式还会令路由 `queue_limit()` 返回 `None`；本轮始终启用鉴权。

### 3. 本地中文路径影响原始打码命令

原始 `deface.exe` 两次因 OpenCV 4.10 无法从中文路径读取 `centerface.onnx` 失败。模型文件存在，Python 读取同一文件字节后 OpenCV 加载成功。

为继续测量，仅在测试子进程的 `sitecustomize.py` 中将非 ASCII 路径的模型加载转换为字节加载。没有修改应用或已安装依赖。后续打码结果依赖此测试兼容处理，不能宣称原始环境已修复。另以 UTF-8 模式运行后续测试，避免 GBK 解码子进程日志的问题。原始失败保存在 `media-initial-failure.json`。

头发模式 `face_hair_primary` 在本地人脸补测中另外失败：MediaPipe 报无法找到 `face_detection_full_range_cpu.binarypb`。只读核对该文件实际存在（260 字节），因此记录为运行时资源加载问题；尚未完成该问题的根因修复或在 ASCII 路径环境中的复测。不能宣称头发打码通过。

## HTTP 响应测量

已登录用户读取 `/api/auth/me`、`/api/production/runs?page=1&page_size=10`、`/api/production/model-options`，三种请求各占约 1/3。使用固定到达速率，不等上一条完成才发送下一条。每档 15 秒，发压调度延迟另有记录。

| 场景 | 请求数 | 成功 | P50 | P95 | P99 |
|---|---:|---:|---:|---:|---:|
| 10 请求/秒 | 150 | 150 | 8.71 ms | 20.55 ms | 32.27 ms |
| 30 请求/秒 | 450 | 450 | 13.03 ms | 27.15 ms | 36.56 ms |
| 60 请求/秒 | 900 | 900 | 18.09 ms | 33.29 ms | 43.95 ms |
| 10 个执行槽位占满时，30 请求/秒 | 450 | 450 | 17.01 ms | 43.47 ms | 61.97 ms |
| 预览排空后，10 请求/秒，10 秒 | 100 | 100 | 10.39 ms | 45.55 ms | 53.05 ms |

这说明上述本地轻查询组合在测试窗口内可处理 60 请求/秒；没有测出其最大稳定容量。混合读取阶段的重任务正在等待模拟供应商，并不代表同一时刻有 10 个 CPU 密集任务并行计算。

## 排队、幂等与恢复验证

- 实测峰值 10 个运行任务，每账号不超过 1 个运行任务。
- 满载快照：36 个等待任务，每账号不超过 3 个；没有超额入队。
- 对同一已接收提交重复请求 20 次，全部返回同一任务 ID。
- 撤销一个等待任务后能接收替代任务。
- 释放模拟供应商阻塞后约 18.966 秒排空。此时累积任务为 104 个成功、1 个主动撤销。
- 预览：持有真实共享预处理锁，逐账号提交不同裁剪参数，确保不是重复请求命中同一预览。36 次请求中 20 次接收、16 次返回 429；P95 95.39 ms。释放锁后对已接收预览执行真实视频处理。
- 20 个已接收预览最终全部达到 `defaced`，没有遗留运行中的预览。
- 约 1 个任务/秒连续提交 60 秒，60 个全部接收并成功完成；提交接口 P95 504.56 ms，含排空总耗时 60.641 秒。这是短时持续负载，不是数小时稳定性验证。
- 实际杀死整个测试服务进程树并重启：带持久化供应商 task_id 的任务在 2.156 秒内恢复成功，原 ID 不变；事件记录为首次提交 1 次、恢复 1 次，没有再次新建供应商任务。
- 另在停机时构造“running + submitting + 没有 task_id”的数据库故障样本；重启后为 `needs_attention / submission_uncertain`。这是明确标注的故障夹具，不是付费服务故障。
- 最终数据库共 167 个任务：165 succeeded、1 cancelled、1 needs_attention；最后一项是上述预期故障夹具。首次突发的 `burst-*` 最终只落库 46 个，与收到的接收响应数量一致；20 个客户端无响应没有形成额外落库任务。12 个租户 SQLite 的完整性检查全部为 `ok`。

## 实际媒体处理

- 640×360、24 fps、3 秒带音轨合成视频：真实 deface 耗时 3.948 秒；输出为 640×368、3 秒。
- 1280×720、24 fps、5 秒带音轨合成视频：真实 deface 耗时 6.697 秒；输出时长、画幅维持一致。
- 两个输入文件的 SHA-256 在处理前后保持一致。
- 6 次真实 FFmpeg 操作，最多 2 个并行：裁剪到 2 秒约 0.248–0.256 秒；慢放到 5 秒约 0.414–0.443 秒。输出全部可探测、时长正确。
- 首批 12 个生产任务走真实冷缓存预处理与模拟供应商，总排空时间 54.744 秒；提交接口本身 P95 4.054 秒。本地预处理共享锁的串行影响不能忽略。
- 合成视频用于吞吐和链路验证，不用于验证人脸遮挡质量。另使用已安装 scikit-image 自带的 `astronaut.png`（无下载）生成 512×512、24 fps、3 秒视频：检测到 1 张人脸，真实 face 打码耗时 4.255 秒，输出可解码、人脸区域有显著像素变化、输入文件不变。静态图片循环不能代表复杂动态人脸、多人和遮挡场景。
- 对同一人脸视频执行 `face_hair_primary` 失败，原因见上文；失败记录也包含在最终汇总。
- 640×360 被 deface 输出为 640×368 的变化已记录；本轮没有修改其编码行为。

## 回归与证据

针对调度、10 槽位、队列原子性、预览隔离、生产 worker、供应商恢复、计时、裁剪、续写恢复/传输的回归：119 passed、1 skipped、1 条第三方弃用警告，44.93 秒。跳过项是 Windows 缺少创建符号链接权限，并非队列功能测试。

HTTP 原始记录共 4,224 条（包括轮询观测，不包括初始化上传、登录和独立恢复脚本的请求）：4,060 个 200、128 个 409、16 个 429、20 个客户端无 HTTP 结果。没有记录到 HTTP 5xx。网络阻断事件记录为 0，即被观测的 Python 进程没有尝试建立非回环连接；供应商函数由本地模拟替代，本轮未触发真实业务付费调用。

修正采集句柄后的应用进程 RSS 峰值约 168.88 MiB；这不含全部媒体子进程，不可作为机器总内存预算。早期采样值 0 和仅采到 Python 启动器的约 4 MiB 数据无效，汇总已排除。采样涉及重启，不能用重启后的低内存值证明无泄漏。

## 下一步建议

先修复过载准入响应：在昂贵处理之前进行低成本限流/容量预检查，并保留创建任务时的原子校验以防并发竞争。加入全站视频等待总量和等待期限；明确繁忙响应及重试提示。对上述变化重新运行同一突发测试，分别验收拒绝延迟与队列正确性。

之后再在与服务器 CPU、内存和部署参数相同的隔离环境下做更长的容量测试。本轮没有真实供应商限流、长视频/大上传、海量历史账号、长期内存稳定性或服务器容量数据。
